# MSP Sentinel: design (v1.0)

Status: **agreed for 1.0**. This is the design of the first release; later features are described in the
[user guide](user-guide.md), [agent.md](agent.md), the [changelog](../CHANGELOG.md) and the [roadmap](ROADMAP.md).

MSP Sentinel is a self-hosted security product for MSPs. It **detects** external exposure and vulnerabilities,
monitors them and alerts on them. It sits alongside MSP Align, which **plans, reports and proves**. Align reads
Sentinel's findings through the API.

**Feature rule:** if it helps the MSP plan, report or prove, it belongs in Align. If it detects or responds, it belongs in Sentinel.

## 1. Decisions

| Area | Decision |
|---|---|
| Stack | Plain PHP 8.4, MariaDB, Bootstrap 5.3 + AdminLTE 4. No framework, no Composer. |
| Scanning | PHP command-line workers call **nmap**, which the MSP installs (not bundled), and PHP's own TLS/HTTP functions. Nuclei comes later. |
| Targets | Typed in, plus suggestions from DNS (A/MX records) and Certificate Transparency (crt.sh). **A suggestion is never scanned until an admin approves it into the client's scope.** |
| Schedule | Scans run from Sentinel's own server: a port check weekly and certificate checks daily, inside each client's scan window. A remote scanner node can be added later. |
| Ports | About 40 risky ports by default, editable per client (see section 6). |
| Roles | Admin, Technician, Viewer. Local accounts with TOTP 2FA. |
| Reports | Executive Summary and Technical Findings in v1.0, built on a shared report engine. Print-ready HTML, with server-side PDF when headless Chromium is installed. Reports carry the MSP's branding. |
| Alerts | In-app notifications, email (a digest per scan plus an immediate email for each new FAIL) and a webhook. ITFlow tickets come in v1.x. |
| ITFlow | Optional ITFlow client and asset ID fields only. No ITFlow API calls in v1. |
| Align | REST API at `/api/v1` with hashed, expiring, revocable bearer tokens (all or chosen clients, optional IP allowlist). Reading is always allowed; triage and queueing scans are opt-in per token. Signed outbound events (webhook) so Align doesn't have to poll. |
| License | AGPL-3.0 |
| Audience | **Any MSP**, not only ours. Each MSP self-hosts its own install and owns its data. No multi-tenant hosting. |
| White-label | A setting per install. By default, reports carry the MSP's branding with a small "Generated by MSP Sentinel" footer. An admin can remove the footer and rename the product in the web UI. |

## 2. Components

1. **Web UI** (`public/index.php` front controller): clients, scope register, targets, findings, scans,
   settings, users, API tokens.
   - Every route checks login and role first.
   - Every POST is CSRF-checked.
   - Every value in a view is escaped.
2. **Scheduler** (`bin/scheduler.php`, run by cron every minute): turns each due schedule into a queued job. It only
   does this for targets in an active, approved scope, and only inside the client's scan window.
3. **Worker** (`bin/worker.php`): takes one job at a time and **rechecks the scope just before scanning**.
   - Ports: runs nmap with `-sV`, a slow timing template and a rate cap. Arguments come from a whitelist and are
     passed as an argument array. A shell string is never used.
   - Certificates and TLS: checks expiry, chain, weak protocols and hostname match.
   - Admin pages: an HTTP GET of `/` on the web ports. It matches the title and headers against a small list of
     signatures, using generic product names only.
4. **Threat feeds** (`bin/feeds.php`, daily):
   - downloads the CISA KEV catalog and EPSS scores;
   - makes rate-limited NVD CVE lookups by CPE (Common Platform Enumeration, a standard product ID), with an
     optional NVD API key.

   All of this is cached locally.
5. **Matcher:** maps each detected product and version to a CPE, then to CVEs. The result is **confirmed** when the
   version is known, or **product found, version unknown** when it isn't. It never guesses a version.
6. **Diff and alerts:** compares each scan with the previous one. It raises "new port", "port closed", "new KEV CVE"
   and "certificate expires in 14 days or less".
7. **API** (`/api/v1/clients`, `/assets`, `/findings`, `/scans`, `/reports`, `/clients/{id}/summary`): paginated,
   with an `updated_since` filter; `POST /findings/{id}/triage` and `POST /clients/{id}/scans` for tokens with those
   permissions; OpenAPI at `/api/v1/openapi.json`. It has its own kernel: no session or cookies (so no CSRF), JSON
   errors, 120 requests a minute per token. Outbound events are signed with HMAC-SHA256.
8. **Report engine:** builds reports from a **frozen snapshot** of findings at a point in time, so a report never
   changes after it's issued.
   - Output is print-ready HTML: A4 or Letter, page breaks, header and footer. Charts are inline SVG made on the
     server (no JavaScript), so they print cleanly.
   - If headless Chromium is installed, Sentinel turns the HTML into a PDF itself. Chromium runs as a separate
     program, is never bundled, and is sandboxed with network access off. Without it, reports still work through
     the browser's "Save as PDF".

## 3. Data model (sketch)

- `users` (with `session_version`: bumping it ends that user's sessions), `user_recovery_codes`, `auth_throttle`
  (sessions themselves use PHP's server-side session store; no `sessions` table is needed)
- `api_tokens` (prefix, keyed hash, all clients or `api_token_clients`, triage/scan flags, IP allowlist, expiry,
  creator, last used, revoked). Added with the API in step 10.
- `clients` (name, itflow_client_id, scan window, timezone, port profile, kill switch)
- `sites` (client, name, itflow_location_id). v1 creates one default site per client. Agents attach here later.
- `scanner_nodes` (name, type local/remote/agent, site, status, last seen). v1 has one: the local worker.
- `scan_authorisations`: the "authorised to scan" record (client, approved_by, approved_at, valid_from/to, document
  reference, notes)
- `scope_entries` (authorisation, type ip/cidr/domain, value). **Nothing is ever scanned unless it matches an entry here.**
  Authorisations can't be edited, only revoked once. This is enforced by the application, not by database
  grants, so anyone with direct database access must not edit them. The audit log records every authorisation as created.
  Scanning code calls `ScopeService::isInScope(clientId, canonicalTarget)` before touching any host, and must also
  check every IP a hostname resolves to.
- `target_suggestions` (client, value, source dns/crtsh, status pending/approved/rejected)
- `assets` (client, ip/hostname, itflow_asset_id, first/last seen)
- `services` (asset, port, protocol, product, version, cpe, banner hash, first/last seen)
- `certificates` (asset, hostname, subject, issuer, not_after, protocols, weaknesses)
- `scans` and `scan_jobs` (type, scanner node, status, start/end, who started it, error, plus a self-contained
  payload of targets and scope so the job can be signed later)
- `scan_log`: an append-only log of every active scan
- `findings`:
  - links: client, site, asset, engagement_id (empty until pen testing exists)
  - source: external / internal / authenticated / pentest (v1 only writes `external`)
  - classification: type, severity FAIL/WARN/INFO, confidence confirmed/possible
  - CVE data: cve_id, KEV flag, EPSS score
  - status: open/resolved/accepted/false_positive, plus the triage note and who made it
  - dates: first/last seen, last checked
- `cve_cache`, `kev_catalog`, `epss_scores`
- `reports` (client, type, period, generated_at, generated_by, snapshot JSON, file hash, PDF path)
- `branding` (MSP name, logo, accent colour, contact details, footer text, "Generated by MSP Sentinel" on/off)
- `notifications`, `settings`, `audit_log`

## 4. Severity

- **FAIL:**
  - a confirmed KEV CVE or a confirmed critical CVE;
  - any of these open to the internet: RDP 3389, SMB 445, Telnet 23, VNC 5900, databases (1433, 1521, 3306, 5432,
    6379, 9200, 27017);
  - a reachable firewall or VPN admin page;
  - an expired certificate.
- **WARN:**
  - a confirmed high CVE;
  - "product found, version unknown" on a product that has KEV entries;
  - FTP open;
  - a certificate expiring within 14 days;
  - weak TLS.
- **INFO:** everything else.
- Accepted and false-positive findings stay visible, with their notes, but they don't count toward FAIL or WARN totals.

## 5. Reports

Goal: reports that are **clean, robust and easy to read**. A client owner should understand the Executive Summary in
two minutes. A technician should be able to act on the Technical Findings report without opening Sentinel.

**In v1.0:**
1. **Executive Summary** (2 pages at most, plain English, no jargon):
   - overall rating (Good / Needs attention / At risk) with a one-line reason
   - top 5 risks, each with "what it means for you" and "what we're doing"
   - totals: open FAILs and WARNs, findings fixed this period, certificates expiring soon
   - a "last checked" date and the scope covered
2. **Technical Findings:**
   - grouped by severity, then by asset
   - each finding shows its evidence (port, banner, certificate details), CVE/KEV/EPSS data, confirmed or possible,
     how to fix it, and first and last seen
   - accepted and false-positive findings are listed separately, with their notes
   - an appendix with the scope, scan dates and the methods used

**Also in v1.0 (0.9.0):** a trend chart (open Fail/Warning at each month end, from daily counts in
`finding_stats`), CSV export of a report's findings, and a monthly schedule per client: both reports are created
after each month and emailed as self-contained HTML attachments to MSP staff (not the client) for review.
Server-side PDF through headless Chromium is not built yet; reports print to PDF from the browser.

**Later (v1.x):** a full Change report (new, fixed and still open), Compliance Evidence Pack (scope approvals, scan
log, results, plus a clear "not a PCI ASV scan" statement), optional server-side PDF, and reports covering several
clients.

**Design rules:**
- Severity is never shown by colour alone. Every colour also has a label and an icon, so reports work printed in
  black and white and for colour-blind readers.
- Reports use plain language with consistent terms, and carry a date and version on every page.
- Reports use the MSP's branding: logo, colour and contact details. A small "Generated by MSP Sentinel" footer can
  be turned off (white-label setting).
- No data outside the client's own scope ever appears in that client's report. Tests check this.
- Every value is escaped in the report templates, the same as in views.

## 6. How Align and ITFlow fit

- **Align:**
  - The connector reads `/summary` and `/findings` per client. Clients are matched on `itflow_client_id`.
  - FAIL and WARN counts feed Align's health score and compliance controls ("external exposure reviewed", "no known
    exploited vulnerabilities").
  - Findings carry their `last checked` date, so they serve as evidence.
  - Some findings become roadmap seeds, for example "Replace firewall: 2 KEV CVEs".
- **ITFlow:** in v1 the IDs are stored so the data lines up later. Tickets and automatic asset matching come in v1.x.

## 7. Default port profile

As built in 0.4.0: TCP only. UDP needs raw sockets (root), and the scanner runs unprivileged on purpose. nmap
runs once per IP, which makes cancel, pause and window checks take effect quickly. Hostnames are scanned
through their resolved addresses, and only addresses that are in scope themselves.

TCP: 21, 22, 23, 25, 53, 80, 110, 135, 139, 143, 389, 443, 445, 465, 587, 636, 993, 995, 1433, 1521, 1723, 2049,
3306, 3389, 4443, 5060, 5432, 5900, 5985, 5986, 6379, 8080, 8443, 9000, 9200, 10443, 27017, plus common firewall
and VPN admin ports. UDP: 161, 500.

## 8. Out of scope for v1

Phased plan for the full suite (internal agent, pen testing): see `ROADMAP.md`. Version 1.0 includes scanner nodes,
sites, a finding `source` and a global/per-client kill switch, so later phases don't need a rewrite.


- internal collector or agent
- nuclei
- ITFlow tickets and sync
- monthly top-1000 port sweep
- remote scanner node
- default-credential checks
- anything that looks like pen testing

Until real pen testing exists, call this product "vulnerability scanning". Sentinel is **not** a PCI ASV scan.

## 9. Tests

- An end-to-end suite runs with a fake `nmap` binary that replays recorded XML, and with mock HTTP servers for NVD,
  KEV, EPSS, crt.sh, DNS, SMTP and the webhook.
- TLS checks run against a local TLS server with made-up certificates.
- Fixtures use only `*.example` names and documentation IP ranges (192.0.2.0/24, 198.51.100.0/24, 203.0.113.0/24).
- No real host is ever scanned in tests.

## 10. Risks and how we handle them

1. **Scanning something outside the scope**, which has legal risk. Scope is checked twice, when the job is scheduled
   and right before the scan, and every active scan is logged.
2. **Setting off clients' intrusion alerts.** Scans are slow, use a short port list, and run only in each client's window.
3. **Wrong CVE matches.** Banners can be faked or unclear. The confirmed/possible split, triage notes and "never
   guess" keep findings honest.
4. **NVD rate limits and outages.** Data is cached and the API key is optional. If NVD is down, the last known data
   is shown with its date.
5. **nmap's license** (NPSL, not plain GPL). Sentinel calls nmap as a separate program and never bundles it. The
   license gets checked again before any packaging.
6. **API token leaks.** Tokens are stored as keyed hashes, expire within a year, can be limited to clients and IP
   addresses, are read-only unless write permissions are ticked, stop working when their creator is no longer an
   active admin, can be revoked, and their last use is logged.
7. **Command injection through targets.** Values are strictly validated as IP, CIDR or domain, and passed as an
   argument array, never through a shell. The worker refuses private address ranges unless the scope explicitly
   allows them.
8. **The PDF renderer reaching the network or reading local files.** Chromium runs with networking off, and it only
   gets self-contained HTML with images and CSS inlined.

## 11. Built for other MSPs

Sentinel is a product other MSPs install themselves, so v1.0 includes the following.

- **Easy install:**
  - a Docker Compose setup, plus a bare-metal install guide
  - a first-run **setup wizard** that checks prerequisites (PHP version and extensions, MariaDB, nmap, optional
    Chromium), creates the first admin and sets the branding
- **Safe upgrades:**
  - idempotent migrations that run automatically
  - a version shown in the footer
  - an opt-in update check. **No telemetry.**
- **Nothing hard-coded to our MSP:**
  - port lists, severity rules, schedules, report wording, paper size (A4/Letter), timezone and date format are
    all settings
  - every interface string goes through one translation function, so other languages can be added later (English
    only in v1.0)
- **Integrations are plug-ins:**
  - a small `Integration` interface (link client, link asset, and later create ticket)
  - ITFlow is the first plug-in
  - other PSAs can be added without touching the core
- **White-label setting:** a product name override in the web UI, and the report footer can be turned off.
- **Security of Sentinel itself.** It holds a map of clients' weak spots.
  - secrets (SMTP password, webhook URLs, API keys) are encrypted at rest with a key kept outside the database
  - an optional IP allowlist for the web UI
  - a hardening guide
  - `SECURITY.md` with a vulnerability disclosure policy
  - SSO (OIDC, including Entra ID) comes in v1.x.
- **Docs shipped with v1.0:**
  - an admin guide and a user guide
  - a **sample scan authorisation form**
  - a responsible-use statement, since scanning laws differ by country
  - `CONTRIBUTING.md` (DCO sign-off) and issue templates

## 12. Build order

1. Repository skeleton: VERSION, LICENSE, README, idempotent migrations, the front controller, auth (2FA, roles),
   CSRF, the test harness
2. Clients and the scope register
3. Targets and discovery
4. Port scan worker
5. Certificates and TLS
6. Threat feeds and CVE matching
7. Findings and triage
8. Reports (report engine, Executive Summary, Technical Findings)
9. Alerts
10. API
11. Packaging and docs: release archive and installer (Ubuntu 24.04 / Debian 12, Nginx), health check, backups,
    update check, data retention, guides, sample authorisation form, responsible-use statement, `CONTRIBUTING.md`.
    (Docker Compose and a web setup wizard were dropped in favour of the installer; they may come later.)

Each feature gets tests, then an independent security review, then fixes and a re-test.
